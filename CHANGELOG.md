# Changelog

All notable changes to neuroschema are recorded here, following [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
While the schema is pre-1.0, a MINOR bump marks a breaking change or a new extension namespace (`.rules/schema-design.md`).

## [Unreleased]

### Changed

- The sensor-field and sensor-layout vectors are regenerated with eegprep at `871bc7f8` (sccn/eegprep#672 and later), the commit NEMAR's processing images run, in place of `edf694c8`; the `vectors` dependency group pins it. Every map, grid and layout matches the previous vectors within the regeneration tolerance (eegprep's grid now comes from MATLAB's `linspace`, which moves some coordinates in the last bit). Two recorded eegprep quirks are fixed upstream and the vectors say so: the `exact_duplicates` case's `eegprep_unmerged_finite_cells` is now the map's finite cell count (eegprep averages coincident sensors, as MATLAB's `griddata` does), and the `nan_values` case's `eegprep_raw_agrees` is now `true` (eegprep drops a value that is not finite with its position); the check behind it gives eegprep the same deviations from the mean as the spec's map. `docs/views/sensor-field.md` describes eegprep at the new commit.

## [0.6.0] - 2026-11-24

Quality views replace figures: a view is data a browser draws, declared with a namespaced, versioned kind (nemarOrg/neuroschema#21, part of nemarOrg/nemar-cli#2324).

**Breaking.** A document valid under 0.5.0 can fail under 0.6.0. The changes that reject one: record-level `dataQuality` `figures` is replaced by the required `views`; each dataset-level distribution requires `unit`; `processingTypes.metricName` allows one colon at most, followed by a letter, and a record-level metric's name is paired with its producer (a bare name with `recipe`, `<plugin>:<name>` with `plugin`); `dataQuality` is closed at its root and in `$defs/record` and `$defs/dataset`; `processingTypes.plugin.name` is `^[A-Za-z][A-Za-z0-9_-]{0,63}$`; `processingTypes.relativeLocation` refuses `%`, `?`, `#`, dot and empty segments, a trailing `/`, leading or trailing spaces and control characters; `dataPaper.doi` takes ASCII `[!-~]+` after the prefix; `dataset_id`, a record's `dataset` and `schema_version` refuse a trailing newline; every `integer` is capped at 2^53 - 1 in magnitude; and `neuroschema.validate` refuses a duplicate member name, `NaN` or `Infinity`, and nesting deeper than 64. Every entry under Changed (breaking) can reject a 0.5.0 document; the tightenings of surfaces new in 0.6.0 are part of their Added entries.

### Added

- `schema/definitions/view.schema.json`: the view declaration (`$defs/view`): key, namespaced `kind` and `kind_version`, optional `base`, caption, source (a plugin or a recipe), scope (`recording`; `subject`, `dataset` and `collection` reserved, with `sources`), parameters, stored `data[]` (role, location, format, size, SHA-256, columns, dimensions, coordinate system, position source) and computed `inputs[]` (a product file or a serving store, each by digest) with a named, versioned `transform`. A kind the registry does not list passes on this envelope; a listed kind is also checked against its own schema. A view's `base` never names a registered preset; a `kind_version` or `base_version` of `true` is no version; a location ending in `.tsv` or `.json`, in any case, declares that format (the extension and the format name each other in both directions); `viewData.size` and `fileInput.size` are at most 4,194,304 (`caps.bytes_per_role`); and in a record entry each view's store inputs carry the entry's `profile`.
- `schema/views/kind.nemar.table.v1.schema.json`: the generic table kind (one TSV file in role `table`, with columns and no dimensions).
- `schema/views/kind.nemar.lines.v1.schema.json`, `kind.nemar.heatmap.v1.schema.json` and `kind.nemar.histogram.v1.schema.json`: the generic line chart (one TSV file in role `values`: a strictly increasing x column along the rows and one numeric series per value column), heatmap (one TSV file in role `values`: one flat cell per stored value, row and column labels, `minmax` or `absmax` limits) and histogram (one JSON file in role `histogram`) kinds, dispatched from `view.schema.json` and registered with open dimension names (`dims: null`). A histogram's bins of unequal width are drawn by density, count over width (the model's `heights`, each bin's `width` and `density`, and `max_density`), `missing` values are counted apart and shown beside the bars, and a bin too wide, or a density too large, for binary64 is `cap_exceeded`.
- `schema/views/content.nemar.histogram.v1.schema.json`: a histogram's content, binned by numeric edges (`edges`, `counts`, `underflow`, `overflow`, optional `unit`; the shape of a `dataQuality` distribution's histogram) or by category (`categories`, `counts`), open for a preset's own members. The registry names it in the role's new `content` member. It may count `missing` values apart.
- `docs/views/generic-kinds.md`: the model a renderer builds for `nemar.table`, `nemar.lines`, `nemar.heatmap` and `nemar.histogram` version 1 and for the fallback (how TSV and JSON files and their cells are read, coordinates, value columns, the readout that snaps to a stored row, the bin rule `[e_i, e_i+1)` with the last bin closed, color limits, caps, a histogram's total capped at 2^53 - 1), the keyboard, data-table and text-alternative views built from the model, the files a refused view still offers for download, and the words a renderer refuses with in the normative order of its checks. A renderer checks a declared size before it fetches a file (`cap_exceeded` before `file_missing` or a digest), verifies each data entry against its own size and digest even when two share a location, holds a coordinate role to the cap on cells, refuses with a word where it would raise (a JSON file nested too deep is `json_invalid`; a preset named as a base shows as a table), refuses NaN in `locate_bin`, and holds no negative zero in any number of a model (counts, totals, limits).
- `nemar.kinds-models.v1` and `nemar.kinds-verdicts.v1`: `views/vectors/kinds-models.v1.json` (models, readouts, bins and refusals every renderer reproduces) and `views/vectors/kinds-verdicts.v1.json` (declarations and contents with the schemas' verdicts, for a renderer without a JSON Schema engine), written by `scripts/generate_kind_vectors.py` (`--check` in the test suite), and the Python reference `neuroschema.views.build_model`. The verdict corpus holds each preset's declarations and `content.nemar.ic-classes.v1` contents, and the vectors cover escaped duplicate names, lone surrogates and noncharacters, nesting 64 and 65 deep, integers past 2^53, URL-escaping locations, names that imitate ICLabel, counts written `-0`, every word and each pair of neighboring checks.
- `views/registry.json` (`neuroschema.views-registry.v1`): kinds, transforms, algorithms, formats (`tsv`, `json`), reserved dimension names and caps. The reserved dimension `sensor` is, with a layout or positions role, that role's name column in row order, and with neither, the names `nemar.sensor-labels.v1` places; `neuroschema.views.ic_activity.CAPS` is the registry's caps.
- `nemar.view-digest.v1`, the SHA-256 of a declaration's RFC 8785 canonical JSON over I-JSON input (no duplicate member names): `docs/views/view-digest.md`, vectors in `views/vectors/view-digest.v1.json`, and the Python reference `neuroschema.views.view_digest` with `parse_declaration`, which reads strict UTF-8 text and refuses duplicate member names. It refuses noncharacters and nesting deeper than 64, has the refusal vector `integer_beyond_binary64` (an integer literal past binary64 range, which `JSON.parse` reads as `Infinity`), and `parse_declaration` refuses an integer literal longer than Python's `int_max_str_digits` with `CanonicalizationError`; `build_model` refuses a declaration with no digest (`declaration_invalid`).
- `neuroschema.views`: the registry reader and the renderer rule (`draw_as`), which draws an unknown kind by its base only when each of the base's roles is valid under the base kind's schema (`meets_role_contract`, `role_schemas`), offering the other files for download, and otherwise shows a table. The role contract requires each role a kind requires exactly once and each optional role at most once, and validates the view's entries in the kind's roles together under the kind schema's `data` subschema, so a rule across roles holds for a preset drawn by its base; `view_validator()` and the content validators check the binary64 reading of a document.
- `processingTypes`: `viewKey`, `kindName`, `transformName`, `roleName`, `dimName`, `formatName` and `recipe`.
- `docs/views.md`: the view vocabulary, the renderer rule, data roles, dimensions, inputs, scope, formats, caps, versioning and what digests prove.
- `nemar.sensor-labels.v1`, sensor positions inferred from channel names, refusing with a reason when the names do not identify one montage: `docs/views/sensor-labels.md`, vectors in `views/vectors/sensor-labels.v1.json`, the pure-Python reference `neuroschema.views.sensor_labels`, and a registry entry. Names are folded by a fixed table (full-width ASCII and the compatibility spaces), never by Unicode normalization, so every runtime reads a name alike, and a key outside ASCII matches nothing; untyped auxiliary channels of Neuroscan caps and clinical EDF exports (`HEO`, `VEO`, `CB1`, `CB2`, `ROC`, `LOC`, `LUC`, `RLC`, `IBI`, `BURSTS`, `SUPPR`) are not counted; EGI's and EEGLAB's fiducial names (`FidNz`, `FidT9`, `FidT10`, `Nasion`, `LeftEar`, `RightEar`) are fiducials; a placement on a HydroCel net needs the recording's `CapManufacturersModelName` (an optional input; `ManufacturersModelName` is not read) to name that net from an exact list, refusing `cap_model_unknown` otherwise, because older EGI nets number their electrodes alike on other positions; and the placed channel the recording's `EEGReference` names (an optional input, normalized without a split at a hyphen, and only on the 10-05 montage and the HydroCel nets, since a BioSemi cap's bank labels are also the ear names) is reported as `reference`, not dropped: a map leaves it out of the interpolation only when all its values are exactly zero (`sidecar_inputs` reads both inputs from the recording's `eeg.json` after BIDS inheritance).
- `views/montages/` (each file also stores `center`, the sphere `nemar.sensor-layout.v1` fits to all its electrodes): twenty standard montages (10-05, seven Electrical Geodesics (EGI) HydroCel nets, six older EGI Geodesic Sensor Nets, six BioSemi caps; the 16, 32 and 64 channel caps carry the bank labels a recording uses) in right-anterior-superior (RAS) meters, generated from MNE-Python 1.13.2 and, for the older EGI nets (EEGLAB's 64-channel net version 2.0 and its 128 and 256 channel nets, with and without Cz, which names never reach, even when a caller passes them in, and which serve only template positions named exactly), EEGLAB's `sample_locs` files copied with EEGLAB's license into `scripts/montage_sources/eeglab` and pinned by SHA-256, by `scripts/generate_montages.py` (uv group `vectors`, with a `--check` mode run in CI; the BioSemi angles are read as written, where MNE-Python truncates them to integers), and `PROVENANCE.json` with each file's MNE or EEGLAB source and digest, MNE-Python's license, EEGLAB's commit and license with its scope, each montage's upstream origin (FieldTrip, EGI, EGI via EEGLAB, BioSemi) and the BioSemi angle corrections.
- `viewData`: optional `montage`, the montage of a role of `template` positions. `montage` requires `position_source` `template`, and a `template` role requires `montage` and `coordinate_system` `n/a` (its positions are RAS meters).
- `nemar.sensor-field.v1`, the scalp map (EEGLAB's topoplot, with eegprep at `edf694c8` as the reference), and the kind `nemar.sensor-field` version 1 that draws with it (`schema/views/kind.nemar.sensor-field.v1.schema.json`: a `values` role of one or more maps over a `sensor` dimension, placed by at most one of an optional `layout` role of name, theta and radius and an optional `positions` role of name, x, y and z, which the view's transform `nemar.sensor-layout.v1` projects; with neither, the sensors are names placed by `nemar.sensor-labels.v1`). `docs/views/sensor-field.md` states the algorithm outright, including what eegprep leaves implicit: sensors within 1e-3 merge at their mean value, fewer than 8 interpolated sensors are refused (as many as `nemar.sensor-labels.v1` needs), the interpolation matrix is solved by lower-upper (LU) decomposition with partial pivoting and no regularization, and maps with nothing to draw are refused with a word. The `absmax` color axis is EEGLAB's (each limit 5% of its magnitude away from zero); the `minmax` axis widens by 5% of the range instead, because EEGLAB's rule clips a map of one sign, such as a spectrum's in decibels; the map interpolates the deviations from the mean of the interpolated values and adds the mean back, so a constant every value carries moves the map and adds no ripple (EEGLAB and eegprep interpolate the raw values), merged values and the mean are computed as `first + sum(x - first) / k`, so a flat field (every usable sensor one value) is that value in every cell, merge groups and values near the binary64 limit included, with no contours and the note `flat_field` ("all sensors have the same value"); a near-flat field (a range at most `1e-9` of the values' magnitude) is one color at the mean, with the note `near_flat` ("all sensors are within <range> of each other"); the parity bound on a cell adds `1e-12` of the map's magnitude to `1e-6` of its range; and the head outline is EEGLAB's cartoon nose and ears, squeezed with the sensors, on a circle at the layout's equator (`0.5 * squeezefac`), given in the vectors.
- `nemar.sensor-layout.v1`, three-dimensional positions to a layout: rotation into the anterior-left-superior (ALS) frame from the Brain Imaging Data Structure (BIDS) frame table, its names spelled as the BIDS schema enum spells them (`MNI152NLin6Asym`, with the coordinate-systems appendix's `MNI152NLin6ASym` read as an alias of it) (no default frame: an unknown one is `frame_unknown`; template positions, `n/a` with a montage, are right-anterior-superior), a center that is never guessed (template positions use their montage's own center, stored in its file, and name their montage exactly as `nemar.sensor-labels.v1` lists it; measured positions use the algebraic sphere through their scalp rows, the rows typed EEG when any row is typed and never a fiducial or a row at (0, 0, 0), and are refused with `positions_flat` when their singular ratio is below 0.05 or their sphere's radius is above 3 times their scale, and with `positions_partial` when they cover too little of the head, the dilution of their center above 4.5, when leaving one of them out moves the fitted center by more than 0.12 of its radius, or when they do not cover the whole head: about the fitted center, with up and front the frame's, each quadrant (front, back, left, right) must hold a position within 38° above the equator, or below it, and no two neighbors in azimuth may be more than 120° apart), and eegprep's `cart2topo` (`docs/views/sensor-layout.md`, `schema/views/transform.nemar.sensor-layout.v1.schema.json`, which `view.schema.json` applies to every view that names the transform; the positions are a stored role that names its own frame, or an input whose frame the parameters name).
- Vectors `views/vectors/sensor-field.v1.json` (32 to 256 sensors, duplicates, near duplicates, sensors outside the head and the interpolation square, values and places that are not finite, constant and refused maps, and measured and template positions projected to maps) and `views/vectors/sensor-layout.v1.json`, written from eegprep by `scripts/generate_view_vectors.py` from inputs frozen in `scripts/view_vector_inputs.json` (`--refresh-inputs` recomputes them), whose `--check` CI runs on Python 3.12.
- The model of `nemar.sensor-field` version 1 in `build_model` (`docs/views/sensor-field.md`, The model and The order of checks), so a scalp map and `nemar.ic-maps` drawn by it are built from their files like every generic kind: the sensors and their stored places from the layout, the positions or the names, which rows a map draws, and each map's word. Measured positions (a layout or positions role) must declare `sensor_type`, in the schema, and a map draws only their rows typed EEG (`no_eeg_sensors` when none is); template positions and names may be untyped (every row drawn when none is typed), and every row of template positions names an electrode of their montage (`template_name_unknown`), any montage of `views/montages` (the older EGI nets included), while a template layout naming a montage it does not hold is refused (`montage_unknown`), since nothing else would stop a layout from being drawn; a row with no place is not drawn; no row typed `SEEG`, `ECOG` or `DBS` is drawn; positions or a layout in `Pixels`, `ACPC` or `ScanRAS` draw no scalp map and are not placed by name (`frame_not_scalp`); positions the projection refuses are placed by name only when every drawn row is typed EEG, and the model says why (`unused_positions`), and otherwise the projection's word takes every map's place; the projection is given the drawn rows' names and types, so a fiducial row is never fitted or drawn; the role that names the sensors (positions, or values with no sensor role; never a layout) may carry the recording's `cap_model` and `reference` (BIDS `CapManufacturersModelName` and `EEGReference`), which a placement by name passes to `nemar.sensor-labels.v1`, and the reference channel it reports is left out of every map only when all its values are exactly zero (`placement.reference`); sensors along the columns placed by a role must carry that role's names, in order (`sensors_mismatch`); an `n/a` place cell is a sensor with no place; integer value columns are maps; and a sensor role with another number of rows than the values falls back with `coords_length`, as the renderer checks it instead of relying on the writer. The model's `placement` carries what a map must state about its positions: their source, `position_source`, the montage, and, for measured positions, that NEMAR does not verify them. Model vectors in `kinds-models.v1.json` cover each source, the fallback, types and frames (an intracranial implant in `ACPC`, `ScanRAS` and `Pixels`, typed and untyped; a real ECoG implant from bids-examples, in Talairach and IXI549Space, frozen in `scripts/ieeg_vector_inputs.json`; an ECoG strip named F1 to C6 in `Other`), every file word in a scalp map, two-fault cases for each pair of neighboring checks it adds, each with its one-fault sibling, and `nemar.ic-maps` with every file its base reads; the verdict corpus holds measured and template positions with and without their types. Building a scalp map's model needs numpy (the `views` extra). A sensor role's `cap_model` and `reference` are at most 256 characters (code points, in ajv as in Python), and the placement words (`montage_unknown`, `template_name_unknown`, `positions_flat`, `positions_partial`) take a map's place, not the view's.

The model vectors' spectrum cases list them under `maps`, with the preset's outcome under `preset`. Without numpy, the tests that draw scalp maps are skipped; the README installs the `views` extra for the full suite. The spectrum and a scalp map's model read one definition of `sensors_mismatch`, `neuroschema.views.models.check_sensor_names`.
- The Python reference renderers `neuroschema.views.sensor_field` and `neuroschema.views.sensor_layout` (with `neuroschema.views.linalg`), numpy only, as the optional extra `views`; the dependency group `vectors` installs eegprep at the reference commit and scipy for the generator.
- `neuroschema.views.optional_roles`: a kind marks a role optional with a `contains` clause whose `minContains` is 0.
- Five presets, version 1, each drawn over a generic kind (`docs/views/presets.md`): `nemar.spectrum` over `nemar.lines` (the column `freq_hz` and the dimension `freq` in Hz, one sensor column in dB each, an optional layout whose rows are the sensors, and the recorded parameters `method`, `window`, `window_s`, `overlap`, `unit` and the required `upper_hz`), `nemar.ic-maps` over `nemar.sensor-field` (the mixing matrix, a required layout and a components table for each component's text row), `nemar.ic-classes` over `nemar.histogram` (a JSON content of `content.nemar.ic-classes.v1`), and the computed `nemar.ic-activity` and `nemar.signal-window` over `nemar.lines`. Each stored preset's branch for a role its base reads takes the base's subschema for that role, so its data meet the base's role contract and a renderer that knows only the base draws it. `nemar.spectrum`'s `welch` is stated in full (mean-detrended windows, mean averaging, one-sided, the 0 Hz row left out); `nemar.ic-classes` labels "summed variance of components classed X"; a `nemar.signal-window`'s `channels` input ends in `_channels.tsv` and its `badsegments` in `_badsegments.tsv`; and one table words every note and digest state (`docs/views/presets.md`, Notes and states).
- `schema/views/content.nemar.ic-classes.v1.schema.json`: components counted by their dominant class, a histogram content by category (`categories`, `counts`) with the `classifier`, `summed_variance_pct` and `n_components`. With the classifier `ICLabel`, spelled exactly `ICLabel` (any other case of the name is refused), the categories are exactly ICLabel's seven classes in its order; any other classifier names its own. A classifier holds no format character (Unicode category Cf) and no white space at its ends, by one explicit character class that Python and JavaScript read alike. The classifier and every category are printable ASCII, and `I`, `l`, `1` and `|` standing in for letters of `ICLabel` are held to its spelling.
- `nemar.ic-activity.v1`, component activations as one plain multiply with no preprocessing: the browser's unmixing matrix (`_servingunmixing.tsv`: the unmixing with the average reference and the store unit's factor to microvolts folded in) times the serving copy's physical values of the decomposition's channels, its columns matched to store rows by `rows` (a decomposition of the serving copy) or by label (one of the archive), with refusals for a channel set that does not match, an unknown unit and a store digest the serving copy publishes other than the declared one, and the state `not_checked` when either digest is absent (`docs/views/ic-activity.md`, `schema/views/transform.nemar.ic-activity.v1.schema.json`). The view declares `badsegments` exactly when the record names the floor's table (`shaded.files`, null only when the floor wrote none), the schema holds it to that, and a view with none carries the note `no_bad_segment_table` ("no bad-segment table; nothing is shaded"). A declared table is verified like a data file (its digest, the TSV grammar, the columns `onset`, `duration` and `label`, found by name in any position) and a fault refuses the whole view, never drawn unshaded; the view shades exactly the rows labeled `shaded.label`. The kind `nemar.ic-activity` declares a display filter that is not part of the decomposition, specified exactly: a Butterworth high-pass of order 2 with a prewarped cutoff, run forward and backward from its steady state over an odd extension of `min(9, n - 1)` samples, so windows shorter than the padding are pinned. The transform's parameters are the record's `browser_transform` block as nemarOrg/nemar-process#81 writes it (matrix, applies_to, note, match, rows, columns, unit, caption, shaded), and the matrix's header must be its `columns`. The kind also declares the window cap and `decomposition_input`, closed and mirroring #81's block (source, preprocessing, channels, the per-row `channel_types` with `channel_types_sha256`, reference, unit, and the store for a serving-copy input); `channel_types_sha256` is the SHA-256 of the RFC 8785 canonical JSON of `{"channel_types": ...}`, the canonicalization of `nemar.view-digest.v1`, which `neuroschema.views.ic_activity.channel_types_sha256` computes and vectors with labels outside ASCII pin. The transform holds the rule that `badsegments` is declared exactly when `shaded.files` is not null, whatever the view's kind, and requires the view parameters its computation reads (`display_filter`, `max_window_s`, `decomposition_input`); `shaded.files` names one `_badsegments.tsv` (never `_samplemask.tsv`), a serving-copy store is matched by `store_row`, never by `label`, and `match` `label` requires a caption string. A renderer checks, in order, the declaration (`declaration_invalid`), the inputs' locations against `matrix` and `shaded.files[0]` (`table_location_mismatch`: every table is the recording's, by the exact stem nemar-process gives its products under the label of the view's recipe), and `decomposition_input.store` against the signal store (`store_mismatch`); a bad-segment table that is missing, or has no row labeled `shaded.label`, refuses the view when the record says ASR repaired a span (`label_unmatched`), and otherwise a table with no such row draws with the note `no_shaded_rows`; a store row the channels table does not name is `channel_row_missing`, a store rate not above 0 `rate_invalid`, and a window outside the store or longer than `max_window_s` `window_outside_store` or `window_too_long`; store rows written as floats are read as the integers they are. The display filter runs over the window and up to a second of real context on each side (`ceil(rate)` samples), padded only at the recording's own ends, and `docs/views/ic-activity.md` states its response (-6 dB at `highpass_hz`, -3 dB at about 1.246 times it) and the transient the context leaves; activations are labeled `a.u.`.

Every schema, montage, registry, example and vectors file the repository publishes is read by it in the tests (but two vectors files whose cases carry an input it refuses), and the vector writers refuse NaN and Infinity.
- `neuroschema.views.download_headers`: every download's headers (RFC 6266 `filename*`, `nosniff`, `application/octet-stream` for a format the registry does not list).
- `dataQuality` record entries may list `views_skipped`, `[{key, kind, reason}]`, the views a run did not write for a recording and why, with a words table in `docs/views.md` (`labels_unusable`, `plugin_failed`, `step_failed`, `step_skipped`, `cap_exceeded`).
- `nemar.record-checks.v1` (`neuroschema.records.check_record`, vectors `views/vectors/record-checks.v1.json`): the cross-field rules of a recording's `dataQuality` entry, which the backend and a renderer run: `metric_producer_mismatch` (a `<plugin>:<name>` metric of another plugin, a bare metric of another recipe), `view_source_mismatch` (a view whose source is another recipe) and `view_key_repeated` (a repeated view key, or a skipped key that repeats or names a view).
- A `dataQuality` distribution's histogram may count `missing` values apart (recordings whose value was missing or not a number).
- CI: a job `ajv` compiles every schema with ajv 8 in strict mode and replays the verdict corpus (`scripts/ajv/check.ts`), and a test flags a bare `.` and the shorthand classes `\s`, `\S`, `\d`, `\w`, `\b` in every schema pattern, which Python and JavaScript read apart.

### Changed (breaking)

- `dataQuality` record level: `figures` is replaced by the required `views` (at most 32 view declarations), and `$defs/figure` is removed.
- `dataQuality` dataset level: each distribution requires `unit` and may carry `description`.
- `processingTypes.metricName`, the key of every `dataQuality` metric, distribution and observed range, is a bare name or `<plugin>:<name>`: one colon at most, and a name after it that starts with a letter. At record level a metric's name is paired with its producer: a bare name requires the producer `recipe`, `<plugin>:<name>` the producer `plugin`.
- `dataQuality` is closed at its root and in `$defs/record` and `$defs/dataset`.
- `processingTypes.plugin.name` takes the grammar of a metric name's prefix (a letter, then letters, digits, `_` and `-`, at most 64 characters).
- `processingTypes.relativeLocation` refuses `%`, `?`, `#`, a `.` or empty segment, a trailing `/`, a leading or trailing space, DEL, C1 controls, the line and paragraph separators U+2028 and U+2029 (its lookaheads match `[\s\S]`, since a JavaScript `.` stops at them) and bidirectional controls, so a location means one file under every URL resolution; `docs/views.md` states how a renderer builds a URL from one.
- `dataPaper.doi` is `^10\.[0-9]{4,9}/[!-~]+$(?!\n)`: explicit ASCII classes in place of `\d` and `\S`, which Python and JavaScript read apart, and no trailing newline (from nemarOrg/neuroschema#20).
- `dataset_id` (`core/dataset.schema.json`), a record's `dataset` (`core/record.schema.json`) and `schema_version` (`neuroschema.schema.json`) end their patterns with `$(?!\n)`, so a trailing newline fails in Python as it does in ajv (closes nemarOrg/neuroschema#20).
- Every `integer` in every schema is capped at 2^53 - 1 in magnitude, and verdicts are on the binary64 reading of a document (an integer past 2^53 is checked as `JSON.parse` reads it).
- `neuroschema.validate` reads a document as I-JSON (`neuroschema.ijson`) and exits 2 on a duplicate member name, `NaN` or `Infinity`, or nesting deeper than 64, which 0.5.0's `json.load` accepted.

### Changed

- Every schema's `$id` is an absolute URI (`https://raw.githubusercontent.com/nemarOrg/neuroschema/v0.6.0/schema/` plus its path), so the relative `$ref`s resolve by RFC 3986 in every engine; `neuroschema.validate` resolves them from `schema/` and fetches nothing. A consumer that vendors the schemas reads the new ids.
- `qualityMetric`: the producer is exactly one of `plugin` and `recipe`, so a recipe's own metric names its recipe.
- `processingTypes`: `figures` leaves the `checkpointName` examples.
- CI and the typo check run on pull requests into `feature/**` branches.

### Documentation

- `docs/views/sensor-layout.md` lists the nine deprecated `UNCInfant` frame names (`UNCInfant0V21` to `UNCInfant2V23`) one by one in place of a range, and a test holds the page to every frame name (#28).

## [0.5.0] - 2026-11-22

Processing metadata for NEMAR's pipeline checkpoints, live progress and quality plugins (nemarOrg/neuroschema#18).

### Added

- `processing` extension namespace: per recording and recipe, each checkpoint's outcome (`passed`, `failed`, `skipped`, with failure code and step); per dataset and recipe, the declared checkpoints and reconciled counts.
- `schema/definitions/checkpointCounts.schema.json`: the counts shape (passed, failed, skipped, total), reused by nemar-cli's live progress object.
- `schema/definitions/qualityMetric.schema.json`: one plugin metric (value, unit, description, optional `bounds` as the plugin-declared valid range, producing plugin).
- `schema/definitions/processingTypes.schema.json`: shared identifier, digest, location and plugin types.
- Examples `examples/dataset-ds002718-processing.json` and `examples/record-ds002718-processing.json`.

### Changed (breaking)

- `dataQuality`: the placeholder fields `quality_score`, `quality_flags` and `assessed_at` are removed. The namespace now requires `level` (`record` or `dataset`) and `recipes`: at record level, typed metrics and figures (PNG, SVG or WebP, with size, SHA-256 and caption) per recipe; at dataset level, the quality control summary per recipe (counts, distributions, `observed_range`, not-processed list), which replaces nemar-process `qc-summary.v1`. Each entry carries the SHA-256 of the signalJourney record it came from.
- `signalJourney`: the placeholder fields `pipeline_id`, `processing_status` and `sj_version` at the namespace root are removed. The namespace now requires `recipes`, one link per recipe with `recipe_version`, `processing_status` (`in_progress`, `completed`, `failed`; `pending` is gone), `location`, `sha256` and `sj_version`.

### Changed

- Every `$ref` below the root schema names its folder (for example `../extensions/dataQuality.schema.json`); resolution targets are unchanged.
- `x-extension-managers`: `dataQuality` and `signalJourney` move from `nemar-pipeline` and `signal-journey` to `nemar-api`, which also writes the new `processing` namespace. `dataQuality` and `signalJourney` now also appear on dataset documents, not only on records.
- Every anchored pattern in the new and changed files ends with `$(?!\n)`, so a trailing newline fails in Python as it does in ajv.

### Documentation

- `docs/extension-managers.md`: the NEMAR backend (`nemar-api`) writes `dataQuality`, `processing` and `signalJourney`.
- New `docs/processing-extensions.md`: levels, writer-enforced invariants, checkpoints, digest and location rules, and the mapping from `qc-summary.v1`.
